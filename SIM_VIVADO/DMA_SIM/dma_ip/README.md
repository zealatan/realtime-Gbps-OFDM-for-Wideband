# DMA Simulation Analysis from an AXI4 Bus Perspective

This document analyzes the DMA simulation project from an **AXI4 bus perspective**.

The key is to separate the design into three different interface domains:

```text
AXI-Lite bus:
  Testbench CPU VIP → DMA control register configuration

AXI4 full bus:
  DMA RDMA/WDMA → memory VIP read/write transactions

AXI-Stream-like path:
  RDMA → dut.v → FIFO → WDMA
```

In other words, this project is not just a simple RTL simulation.  
It can be understood as a small SoC-style DMA simulation that includes:

```text
AXI-Lite control plane
AXI4 full memory-mapped data plane
AXI-Stream-like internal processing datapath
```

---

## 1. Overall Bus Structure

The high-level bus structure is:

```text
                    AXI-Lite
 control VIP  ----------------->  dma_ip_control_s_axi
  Master                         Slave register file
                                      |
                                      | control signals
                                      v
                                 dma_wrapper
                                /           \
                               /             \
                       RDMA read path     WDMA write path
                            |                 |
                            | AXI4 Read       | AXI4 Write
                            v                 v
                    slv_m00_axi_vip memory model
```

Between RDMA and WDMA, there is an internal stream-style datapath rather than a memory-mapped AXI bus.

```text
AXI4 Read
  Memory VIP
      ↓
  RDMA
      ↓
  AXI-Stream-like handshake
      ↓
  dut.v
      ↓
  FIFO
      ↓
  WDMA
      ↓
AXI4 Write
  Memory VIP
```

## 2. AXI Interfaces in the Design

This project contains three major interface types.

---

### 2.1 AXI-Lite Control Interface

Relevant files:

```text
dma_ip_tb.sv
  control_dma_ip_vip

dma_ip_top.v
  s_axi_control_*

dma_ip_control_s_axi.v
  AXI-Lite slave register file
```

Role:

```text
The CPU-like testbench writes and reads DMA control registers.
```

For example, the testbench configures registers such as:

```text
ADDR_RDMA_TRANSFER_BYTE = 1024
ADDR_RDMA_MEM_PTR       = 0x0000
ADDR_WDMA_TRANSFER_BYTE = 1024
ADDR_WDMA_MEM_PTR       = 0x0400
ADDR_VALUE_TO_ADD       = 1
ADDR_AP_CTRL            = 1
```

Therefore, AXI-Lite is not used to move the main payload data.  
It is used as the **control bus** for configuring the DMA IP.

---

### 2.2 AXI4 Full Memory Interface

Relevant files:

```text
dma_ip_top.v
  m00_axi_*

dma_wrapper.v
  m00_axi_*

RDMA:
  hls_rdma.v
  hls_rdma_gmem_m_axi.v

WDMA:
  hls_wdma.v
  hls_wdma_gmem_m_axi.v

testbench:
  slv_m00_axi_vip
```

Role:

```text
The DMA engine generates real memory read/write transactions.
```

The master/slave relationship is:

```text
dma_ip_top / dma_wrapper = AXI4 Master
slv_m00_axi_vip          = AXI4 Slave Memory
```

The `m00_axi_*` interface represents the memory-mapped AXI4 full interface used by the DMA IP to access external memory, such as DDR.

---

### 2.3 AXI-Stream-like Internal Interface

Relevant files:

```text
dma_wrapper.v
dut.v
sync_fifo.v
```

Main signals:

```verilog
out_r_din
out_r_write
out_r_full_n

in_r_dout
in_r_empty_n
in_r_read
```

These signals are not a standard AXI4 memory-mapped interface.  
However, conceptually they behave very similarly to AXI-Stream `valid / ready / data` signals.

```text
out_r_write  ≈ tvalid
out_r_full_n ≈ tready
out_r_din    ≈ tdata

in_r_empty_n ≈ tvalid
in_r_read    ≈ tready
in_r_dout    ≈ tdata
```

## 3. AXI-Lite Write Transaction

In the testbench, register writes are generated by the following task:

```systemverilog
task automatic blocking_write_register(input bit [31:0] addr_in, input bit [31:0] data);
  axi_transaction wr_xfer;
  axi_transaction wr_rsp;

  wr_xfer = ctrl.wr_driver.create_transaction("wr_xfer");
  wr_xfer.set_driver_return_item_policy(XIL_AXI_PAYLOAD_RETURN);
  assert(wr_xfer.randomize() with {addr == addr_in;});
  wr_xfer.set_data_beat(0, data);

  ctrl.wr_driver.send(wr_xfer);
  ctrl.wr_driver.wait_rsp(wr_rsp);
endtask
```

One call to this task creates one AXI-Lite write transaction.

An AXI-Lite write uses three channels:

```text
AW channel: write address
W  channel: write data
B  channel: write response
```

A single register write transaction proceeds as follows:

```text
1. AWVALID/AWREADY handshake
   → write address transfer

2. WVALID/WREADY handshake
   → write data transfer

3. BVALID/BREADY handshake
   → write response transfer
```

For example:

```systemverilog
blocking_write_register(ADDR_VALUE_TO_ADD, 32'd1);
```

This can be interpreted on the AXI-Lite bus as:

```text
AWADDR  = 0x24
AWVALID = 1
AWREADY = 1
  → address handshake

WDATA   = 0x00000001
WSTRB   = 0xF
WVALID  = 1
WREADY  = 1
  → data handshake

BRESP   = OKAY
BVALID  = 1
BREADY  = 1
  → response handshake
```

As a result, the corresponding internal register in `dma_ip_control_s_axi.v` is updated, and the `value_to_add` signal is generated.

```text
AXI-Lite write to ADDR_VALUE_TO_ADD
    ↓
internal register update
    ↓
value_to_add = 32'h00000001
    ↓
dut.ctrl_constant = value_to_add[7:0]
```

---

## 4. AXI-Lite Write FSM in `dma_ip_control_s_axi.v`

The write FSM in `dma_ip_control_s_axi.v` is relatively simple.

```verilog
assign AWREADY = (wstate == WRIDLE);
assign WREADY  = (wstate == WRDATA);
assign BVALID  = (wstate == WRRESP);
```

The state transition is:

```text
WRIDLE → WRDATA → WRRESP → WRIDLE
```

Meaning of each state:

```text
WRIDLE:
  Wait for the AW address channel.

WRDATA:
  Wait for the W data channel.

WRRESP:
  Send the B response.
```

Therefore, this AXI-Lite slave is structurally designed as:

```text
Receive AW first → receive W next → send B response
```

Important study point:

In the AXI-Lite specification, the AW channel and W channel are independent.  
In theory, address and data can arrive independently.

However, this implementation is closer to a simple HLS-style AXI-Lite slave.  
It expects the address phase first, followed by the data phase.

The current Xilinx VIP transaction sequence matches this behavior, so the simulation passes.

For stronger verification, the following cases would be useful:

```text
1. AW and W arrive in the same cycle.
2. AW arrives first and W arrives later.
3. W arrives before AW.
4. BREADY is delayed.
```

## 5. AXI-Lite Read Transaction

The read task in the testbench is:

```systemverilog
task automatic read_register(input bit [31:0] addr, output bit [31:0] rddata);
  axi_transaction rd_xfer;
  axi_transaction rd_rsp;
  bit [31:0] rd_value;

  rd_xfer = ctrl.rd_driver.create_transaction("rd_xfer");
  rd_xfer.set_addr(addr);
  rd_xfer.set_driver_return_item_policy(XIL_AXI_PAYLOAD_RETURN);

  ctrl.rd_driver.send(rd_xfer);
  ctrl.rd_driver.wait_rsp(rd_rsp);

  rd_value = rd_rsp.get_data_beat(0);
  rddata = rd_value;
endtask
```

An AXI-Lite read uses two channels:

```text
AR channel: read address
R  channel: read data
```

The read transaction proceeds as follows:

```text
1. ARVALID/ARREADY handshake
   → read address transfer

2. RVALID/RREADY handshake
   → read data transfer
```

For example:

```systemverilog
read_register(ADDR_AP_CTRL, lite_rddata);
```

This appears on the AXI-Lite bus as:

```text
ARADDR  = 0x00
ARVALID = 1
ARREADY = 1
  → read address handshake

RDATA   = AP_CTRL register value
RVALID  = 1
RREADY  = 1
  → read data handshake
```

When reading `ADDR_AP_CTRL`, the returned bits are usually:

```text
AP_CTRL bit[0] = ap_start
AP_CTRL bit[1] = ap_done
AP_CTRL bit[2] = ap_idle
AP_CTRL bit[3] = ap_ready
```

The testbench uses polling to monitor DMA state:

```text
1. Read AP_CTRL.
2. Check ap_idle.
3. Write ap_start to AP_CTRL.
4. Read AP_CTRL.
5. Check ap_done.
```

## 6. AXI4 Full Memory Bus

The `m00_axi_*` interface is an AXI4 full bus.

AXI4 full has five channels:

```text
AW channel : write address
W  channel : write data
B  channel : write response

AR channel : read address
R  channel : read data
```

In this project, RDMA and WDMA use different channel groups.

```text
RDMA:
  Uses AR channel
  Uses R channel

WDMA:
  Uses AW channel
  Uses W channel
  Uses B channel
```

So:

```text
RDMA → AXI4 read channels
WDMA → AXI4 write channels
```

This structure is visible in `dma_wrapper.v`.

---

## 7. RDMA: AXI4 Read Transaction

Current testbench configuration:

```text
USER_TRANSFER_LEN    = 1024 bytes
C_M00_AXI_DATA_WIDTH = 64 bits = 8 bytes
```

Therefore, the total number of data beats is:

```text
1024 bytes / 8 bytes per beat = 128 beats
```

RDMA reads data from the source buffer.

```text
source address = 0x0000
transfer size  = 1024 bytes
```

The AXI4 read sequence is:

```text
1. Issue a read address burst through the AR channel.
2. Receive data beats through the R channel.
3. Check RLAST on the final beat.
```

Conceptually:

```text
ARADDR  = 0x0000
ARSIZE  = 3          // 2^3 = 8 bytes per beat
ARBURST = INCR
ARLEN   = burst_len - 1

ARVALID/ARREADY handshake
    ↓
RVALID/RREADY handshakes
    ↓
RDATA beat 0
RDATA beat 1
...
RDATA final beat with RLAST = 1
```

Whether this becomes one 128-beat burst or several smaller bursts depends on the internal HLS AXI master implementation.  
This should be confirmed in the waveform.

Logically, however, the total transferred amount is 128 beats.

Master/slave direction:

```text
RDMA master                      Memory VIP slave
-------------------------------------------------
ARVALID  ---------------------->
         <---------------------- ARREADY

         <---------------------- RVALID, RDATA
RREADY   ---------------------->
         <---------------------- RLAST on final beat
```

The received `RDATA` is converted into an internal stream.

```text
m00_axi_rdata
    ↓
hls_rdma
    ↓
out_r_din
out_r_write
out_r_full_n
```

## 8. Internal Stream: RDMA → dut → FIFO

The data received from the AXI4 read bus does not go directly to WDMA.

```text
AXI4 RDATA
  ↓
RDMA
  ↓
out_r_din / out_r_write / out_r_full_n
  ↓
dut.v
  ↓
sync_fifo
  ↓
in_r_dout / in_r_empty_n / in_r_read
  ↓
WDMA
```

This section is not an AXI memory-mapped bus.  
However, the valid-ready handshake is very similar to AXI-Stream.

RDMA output side:

```text
out_r_write  = valid
out_r_full_n = ready
out_r_din    = data
```

Handshake condition:

```text
out_r_write && out_r_full_n
```

In `dut.v`, these signals are connected as:

```verilog
.s_axis_tvalid(out_r_write),
.s_axis_tready(out_r_full_n),
.s_axis_tdata (out_r_din)
```

RDMA drives `out_r_write = 1` when it has valid data.  
The downstream block asserts `out_r_full_n = 1` when it is ready to accept data.

`dut.v` adds `value_to_add` to each 8-bit lane.

Example:

```text
input  64-bit beat:  07 06 05 04 03 02 01 00
output 64-bit beat:  08 07 06 05 04 03 02 01
```

## 9. WDMA: AXI4 Write Transaction

WDMA receives data from the FIFO and writes it to destination memory.

Current configuration:

```text
destination address = 0x0400
transfer size       = 1024 bytes
bus width           = 8 bytes
total beats         = 128 beats
```

The AXI4 write sequence is:

```text
1. Issue a write address burst through the AW channel.
2. Send write data beats through the W channel.
3. Assert WLAST on the final W beat.
4. Receive a write response through the B channel.
```

Conceptually:

```text
AWADDR  = 0x0400
AWSIZE  = 3          // 8 bytes per beat
AWBURST = INCR
AWLEN   = burst_len - 1

AWVALID/AWREADY handshake
    ↓
WVALID/WREADY handshakes
    ↓
WDATA beat 0
WDATA beat 1
...
WDATA final beat with WLAST = 1
    ↓
BVALID/BREADY handshake
BRESP = OKAY
```

Master/slave direction:

```text
WDMA master                       Memory VIP slave
-------------------------------------------------
AWVALID, AWADDR  --------------->
                  <-------------- AWREADY

WVALID, WDATA    --------------->
                  <-------------- WREADY
WLAST on final beat

                  <-------------- BVALID, BRESP
BREADY           --------------->
```

## 10. AXI4 Read/Write Concurrency

A key point in this design is:

```text
RDMA uses only the read channels.
WDMA uses only the write channels.
```

Although both are connected to the same `m00_axi` interface, the actual channel usage is separated:

```text
RDMA → AR/R channels
WDMA → AW/W/B channels
```

AXI4 read and write channels are independent, so read and write transfers can overlap to some extent.

In an ideal case, the following pipeline is possible:

```text
RDMA reads beat N from memory
    ↓
dut processes beat N
    ↓
FIFO stores beat N
    ↓
WDMA writes beat N-k to memory
```

Therefore, AXI4 read and write activity can overlap.

However, from a data dependency perspective, WDMA must wait for processed data from RDMA → dut → FIFO.

```text
WDMA write data availability depends on RDMA → dut → FIFO.
```

## 11. Backpressure Perspective

The most important AXI principle is:

```text
A transfer happens only when VALID && READY.
```

In this project, backpressure can occur at three levels.

---

### 11.1 AXI4 Memory Read Side

```text
ARVALID && ARREADY
RVALID  && RREADY
```

If the memory VIP delays `ARREADY`, the RDMA read request is delayed.  
If the memory VIP delays `RVALID`, read data delivery is delayed.

---

### 11.2 Internal Stream Side

```text
out_r_write    && out_r_full_n
w_in_r_empty_n && w_in_r_read
in_r_empty_n   && in_r_read
```

If the FIFO becomes full, the ready signal deasserts.  
This backpressure can propagate backward through `dut.v` and eventually to the RDMA side.

---

### 11.3 AXI4 Memory Write Side

```text
AWVALID && AWREADY
WVALID  && WREADY
BVALID  && BREADY
```

If the memory VIP delays `WREADY`, WDMA write data is stalled.  
This may fill the FIFO, which can eventually stall the RDMA read path as well.

The current testbench mostly uses a no-backpressure memory model:

```systemverilog
rgen.set_ready_policy(XIL_AXI_READY_GEN_NO_BACKPRESSURE);
m00_axi.wr_driver.set_wready_gen(rgen);
m00_axi.wr_driver.set_awready_gen(rgen);
m00_axi.rd_driver.set_arready_gen(rgen);
```

Therefore, the current simulation is close to an ideal memory environment.

Random transaction or random backpressure modes can be enabled later to test more realistic stall conditions.

## 12. AXI Transaction Timeline

The complete simulation can be described as the following sequence of bus-level events:

```text
[0] Testbench backdoor memory write
    - Not an AXI bus transaction
    - Directly initializes the internal memory of the memory VIP

[1] AXI-Lite writes
    - RDMA transfer byte
    - RDMA source address
    - WDMA transfer byte
    - WDMA destination address
    - value_to_add

[2] AXI-Lite read polling
    - Read AP_CTRL
    - Check ap_idle

[3] AXI-Lite write
    - AP_CTRL = 1
    - Generate ap_start

[4] AXI4 read
    - RDMA issues AR transaction
    - Memory VIP returns RDATA beats

[5] Internal stream processing
    - RDMA output stream
    - dut adds +1
    - FIFO buffers data

[6] AXI4 write
    - WDMA issues AW transaction
    - WDMA sends WDATA beats
    - Memory VIP returns BRESP

[7] AXI-Lite read polling
    - Read AP_CTRL
    - Check ap_done

[8] Testbench backdoor memory read
    - Not an AXI bus transaction
    - Directly reads destination memory for result checking
```

Important point:

```text
backdoor_memory_write/read are not AXI transactions.
```

They directly access the internal memory of the VIP memory model.  
Actual AXI bus traffic occurs only during register accesses and DMA memory accesses.

## 14. Strengths of This Design from an AXI Perspective

From an AXI bus perspective, this simulation has several strengths.

```text
1. The AXI-Lite control path and AXI4 memory path are clearly separated.

2. AXI VIP is used, so the master/slave bus model is explicit.

3. RDMA uses the read channels, while WDMA uses the write channels.

4. Backdoor memory initialization and checking separate result verification from bus traffic generation.

5. The internal stream processing block makes this more meaningful than a simple memory copy test.
```

From a portfolio perspective, this is stronger than a basic RTL testbench because it resembles a real SoC/DMA integration environment.

## 15. Limitations and Next Verification Points

---

### 15.1 Missing AXI-Lite Corner Cases

The current VIP sequence generates normal register transactions.

For stronger AXI-Lite verification, the following cases should be added:

```text
AWVALID first, WVALID delayed
WVALID first, AWVALID delayed
AW and W in the same cycle
BREADY delayed
ARVALID followed by delayed RREADY
Invalid address access
WSTRB partial write
```

The `WSTRB` partial write case is especially useful because the RTL appears to include write-mask logic.

---

### 15.2 Limited AXI4 Memory Backpressure Testing

The current memory model is close to ideal:

```systemverilog
XIL_AXI_READY_GEN_NO_BACKPRESSURE
```

Additional tests should include:

```text
ARREADY delay
RVALID inter-beat delay
AWREADY delay
WREADY delay
BVALID delay
Random backpressure
```

These tests are necessary to determine whether the DMA behaves robustly under stall conditions.

---

### 15.3 Limited Burst Boundary Testing

The current case is clean and aligned:

```text
transfer size = 1024 bytes
source address = 0x0000
destination address = 0x0400
```

Additional useful cases:

```text
transfer size = 8 bytes
transfer size = 64 bytes
transfer size = 1024 bytes
transfer size = 4096 bytes
aligned source address
aligned destination address
unaligned address negative test
4KB boundary crossing test
```

In AXI4, bursts must not cross 4KB boundaries.  
The HLS AXI master may automatically split such bursts, but this should be confirmed in the waveform.

---

## 16. Final Summary

From an AXI4 bus perspective, the simulation can be summarized as:

```text
AXI-Lite:
  control_dma_ip_vip master
    → dma_ip_control_s_axi slave
    → register configuration

AXI4 read:
  hls_rdma master
    → slv_m00_axi_vip memory slave
    → source buffer read

Internal stream:
  hls_rdma
    → dut.v
    → sync_fifo
    → hls_wdma

AXI4 write:
  hls_wdma master
    → slv_m00_axi_vip memory slave
    → destination buffer write
```

The most important AXI-level interpretation is:

```text
AXI-Lite is the control plane for configuring the DMA.
AXI4 full is the data plane for moving memory data.
The RDMA → dut → FIFO → WDMA path is the internal processing datapath.
```

A good waveform study order is:

```text
1. AXI-Lite register writes
2. AP_CTRL start write
3. AXI4 AR/R read burst
4. RDMA → dut stream handshake
5. AXI4 AW/W/B write burst
6. AP_CTRL done read
```

Following this order makes it clear how AXI bus transactions form the complete DMA operation.
