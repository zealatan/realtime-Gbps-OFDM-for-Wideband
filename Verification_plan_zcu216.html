RFSoC ZCU216 Synchronizer Verification Plan

A synchronizer porting and verification plan that reuses the same OFDM test vectors while separating Stage 1: RTL Simulation Verification from Stage 2: FPGA/ZCU216 Board Test.

Core principle:
Use one shared test-vector source. In Stage 1 RTL, compare internal stage-by-stage golden signals. In Stage 2 FPGA, compare final events through DDR-based loopback.

0. Current RFDC Bring-up Status Update

Passed milestone:
The PS + RFDC Block Design based RF loopback passed the FFT peak-location match test. This proves that the DAC → wire/RF loopback → ADC → sample capture → FFT path is alive and that the intended frequency component exists in the captured ADC I/Q samples.

Figure 0. Board verification flow from the current state
Verification stepWhat it provesNext action
RFDC FFT peak match The I/Q sample stream is alive inside the wire loopback. Complex-sample convention is not fully verified yet. Inject +9.6 MHz and -9.6 MHz tones and confirm FFT +40/-40 bins.
PL BYPASS The data/valid/ready/TLAST path between RFDC AXIS and the custom PL shell is correct. Run ADC→BYPASS→DMA/DDR→PS readback and confirm the FFT peak matches the previous result.
DDR TX/RX loop Verifies the full board data path: PS-written DDR waveform goes to DAC, and ADC capture returns to DDR. Expand in this order: single tone → ±tone → multi-tone → known OFDM symbol.
RX SYNC insertion This enters the stage where the synchronizer RTL itself is tested on the board, separated from RFDC/DMA issues. Keep mode=0 bypass and mode=1 sync_enable, then compare against golden C/Python.
Important: The FFT peak match proves that the RF path is alive. For OFDM/SYNC confidence, I/Q direction, packing order, sign extension, TLAST/sample count, and DDR alignment must be separately verified in the BYPASS stage.

9. Final Recommended Flow

Figure 13. Final execution order
Final conclusion:
In Stage 1 RTL, use the same input vector and compare internal fixed-point stages. In Stage 2 FPGA, place the same vector in DDR and compare final events. This keeps RTL/FPGA/RF results tied to one vector ID and makes debugging much easier.
