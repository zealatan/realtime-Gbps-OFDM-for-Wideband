ISS-22highopenrtl
frac_corrector m_axis_tready floating -> ptr stuck at 2, fake 7221 beats
Diagnosis revised after deeper probe: frac_cfo_frame_corrector_top.m_axis_tready (= frac_m_tready wire in phase3_sync_top) was DRIVEN BY NO ONE. meyr_slot_frontend (the immediate downstream consumer) has no s_tready output port (always-ready sink). The wire was declared but never assigned -> X/Z value. corr_accept = play_hold_valid && corr_tready evaluated as X, halting the FSM in S_CORRECT at play_rd_ptr=2. The 7221 'beats' counted on m_axis were X-evaluated-as-1 spurious events.
FIXED 2026-06-17 night: `assign frac_m_tready = 1'b1;` added in phase3_sync_top.v (single line). After fix, ptr progresses 0->576 normally, S_DONE reached, frac_done pulses correctly per frame, FSM cycles cleanly.
ISS-24highopenrtl
Wrapper M_AXIS duty drops to ~50% with Meyr loop active
After ISS-22 fix (frac_m_tready=1), the wrapper's m_axis emits 576 real beats over ~1150 cycles = ~50% duty (rotator pipeline natural rate). Previously the smoke gate measured ~95% duty -- but that was X-prop garbage from the floating tready being counted as 'valid' beats. The new measurement is honest. For the project spec '250 Msps continuous, zero drops', the wrapper FSM needs concurrent Meyr processing (slot k FFT/IFFT running while slot k+1 enters frac_corrector). Currently the wrapper is strictly one-shot (S_IDLE → S_RUN waits for Meyr → S_DONE → S_IDLE). This serializes throughput to ~1 frame per Meyr-latency.
Architecture change: make wrapper FSM accept the next start as soon as frac_corrector goes idle, not after meyr_cfo_valid. Pipeline Meyr completion separately from start re-arm. P5-CONT-SMOKE/NIGHTLY/ROBUST/CORRECTED gates were demoted to required=False until this is fixed -- their assumptions break with realistic per-frame cycling.
